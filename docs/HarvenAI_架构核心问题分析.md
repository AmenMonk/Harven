## 问题一：到底谁在回答？—— AI 身份归属与效率

### 1.1 当前架构：谁在"说话"？

```
用户消息
  │
  ▼
┌──────────────────────────────────────┐
│         web_app.py (/api/chat)        │  ← Flask 服务器
│   判断 active_provider 是哪条路径     │
├────────────────┬─────────────────────┤
│  云端路径       │  本地 Ollama 路径    │
│  (简化版)       │  (完整版)            │
└────────┬───────┴────────┬────────────┘
         │                │
         ▼                ▼
  ┌──────────────┐  ┌──────────────────┐
  │ 直接调云端API │  │ ConversationEngine│  ← 三段式查询
  │ 跳过安全检查  │  │  morality → kb   │
  │ 跳过知识库    │  │  → web → llm     │
  │ 跳过记忆注入  │  │  → 记忆/画像/任务 │
  └──────────────┘  └──────────────────┘
         │                │
         ▼                ▼
     DeepSeek/Kimi     Ollama/Qwen2.5
     /GPT/Claude...    (本地大模型)
```

### 1.2 真相：两层"谁"在协作

| 层 | 谁 | 做什么 | 类比 |
|----|-----|--------|------|
| **助理层** | Harven AI（Flask + Engine + 各种模块） | 管理上下文、记忆、安全、工具调度、前后处理 | 秘书/管家 |
| **大脑层** | 大模型（Ollama 或云端 API） | 基于上下文生成自然语言文本 | 专家/顾问 |

**结论：最终回答是"Harven AI + 大模型"的联合产物。** Harven 负责"知道你是谁、记得什么、安不安全、该查什么"，大模型负责"组织语言说出来"。

**跟 OpenAI 的 ChatGPT 对比**：ChatGPT 只有一层——模型直接面对用户，靠 system prompt 做所有事。Harven AI 多了一层可控的"助理层"，这层可以做 ChatGPT 做不了的事（安全过滤、知识库增强、记忆注���、设备绑定）。

### 1.3 当前最大的效率/合理性问题 🔴

**云端路径跳过了全部安全+增强逻辑！**

看 `web_app.py` 第 195-257 行：
```python
if active_provider != 'ollama':
    # ===== 云端模型路径 =====
    # ❌ 没有 morality 安全分析！
    # ❌ 没有知识库增强！
    # ❌ 没有联网搜索！
    # ❌ 没有 Active Memory！
    # ❌ 没有用户画像注入！
    # ✅ 只有 GitHub 下载 + 直接调 API
```

**这不是故意的设计，是历史遗留**：云端路径是早期写的简化版，后来三段式查询的诸多增强（浏览器、图片生成、记忆注入等）只加到了本地路径。

**后果**：
1. 用户切换到 DeepSeek 时，之前的知识库完全没用
2. 用户画像不会注入到云端对话中
3. 功德行安全检测对云端模型无效（危险！）
4. 记忆系统对云端路径形同虚设

### 1.4 最合理的改进方案

**统一两条路径**：不管用本地模型还是云端模型，都走同一套预处理流程。

```
改进后的架构：
用户消息
  │
  ▼
┌─────────────────────────────────────────┐
│         统一预处理层（不管本地/云端）        │
│  ① 锁机检查                               │
│  ② 功德行分析（always！）                  │
│  ③ 插件匹配                               │
│  ④ 图片生成意图                           │
│  ⑤ Active Memory 注入                     │
│  ⑥ 知识库检索                             │
│  ⑦ 联网搜索                               │
│  ⑧ 用户画像 + 记忆上下文注入                │
├─────────────────────────────────────────┤
│         模型调用层                         │
│  ┌──────────┐  ┌───────────────────────┐ │
│  │ Ollama   │  │ MultiModelManager     │ │
│  │ (本地)   │  │ (DeepSeek/GPT/Claude) │ │
│  └──────────┘  └───────────────────────┘ │
├─────────────────────────────────────────┤
│         统一后处理层                       │
│  ⑨ 记忆提取 → 画像更新 → 任务管理 → 快照  │
└─────────────────────────────────────────┘
```

**具体实现**（改动量不大）：
1. 把 web_app.py 第 195-257 行的云端路径废弃
2. 让 ConversationEngine 支持外部模型（它已经有 `use_external` 判断了！）
3. engine.py 第 531-538 行已经有判断逻辑，只需要让云端路径也走这个分支

**本质就是**：ConversationEngine.send() 已经支持外部模型了（通过 `use_external` 变量），但 web_app.py 的 `/api/chat` 在 `active_provider != 'ollama'` 时完全绕过了 ConversationEngine。修复就是让云端路径也走 ConversationEngine。

## 问题二：安全——下载外部内容如何保证安全？AI 如何不崩溃？

### 2.1 OpenClaw 安全性为什么差

OpenClaw 的安全模型是 **"Docker + 签名验证"** 的单层防护：

```
OpenClaw 安全模型：
  用户 → Gateway → Docker 容器（代码执行）
                      ↓
              如果容器配置错了 = 裸奔
              如果 Skills 没签名 = 供应链攻击
              如果 SSRF 没过滤 = 内网穿透
```

**OpenClaw 的真正风险**：
1. **Skills 供应链攻击**：从 ClawHub 装第三方技能时，技能可以执行任意代码
2. **Prompt Injection**：渠道消息可能包含恶意指令
3. **单点依赖 Docker**：Docker 没装/配错 = 完全无隔离
4. **渠道即入口**：50+ 渠道 = 50+ 攻击面

### 2.2 Harven AI 当前安全现状

#### ✅ 已有的安全层

| 层 | 机制 | 效果 |
|----|------|------|
| **内容安全** | 功德行 v2.0（LLM复核+窗口计数+分级锁死） | 阻止有害内容输入/输出 |
| **数据隔离** | 三库物理隔离（隐私/过渡/商用独立SQLite） | 一库被攻破不影响其他 |
| **设备安全** | 五维指纹绑定（MAC+CPU+BIOS+主板+磁盘） | 防止复制到其他机器 |
| **代码执行** | Docker优先 + 子进程降级 | 恶意代码隔离执行 |
| **操作审批** | requireApproval 三级分级 | 危险操作需确认 |
| **下载安全** | GitHub下载仅文本文件，跳过二进制>5MB | 有限的下载过滤 |
| **容错设计** | 所有模块 try/except，一个失败不阻塞全局 | 服务不会因一个模块崩溃 |

#### 🔴 当前安全盲区

| # | 盲区 | 严重程度 | 说明 |
|---|------|---------|------|
| 1 | **云端路径跳过安全检测** | 🔴 严重 | web_app.py 中 active_provider != 'ollama' 时，moral kernel 不执行 |
| 2 | **无 SSRF 防护** | 🟡 中等 | 用户可以让 AI 访问内网地址（`http://192.168.1.1`） |
| 3 | **无输入净化** | 🟡 中等 | 知识库导入的外部文件未做脚本/宏扫描 |
| 4 | **无速率限制** | 🟡 中等 | 外部 API 调用没有限流，可能被滥用或触发账单 |
| 5 | **无熔断器** | 🟡 中等 | 外部 API 反复失败时会每次重试，浪费资源 |
| 6 | **Ollama 进程无守护** | 🟡 中等 | Ollama 崩溃后需要手动重启 |
| 7 | **下载内容未深度扫描** | 🟡 中等 | GitHub 下载只检查文件类型，不检查内容（嵌入的恶意代码） |
| 8 | **内存泄漏风险** | 🔵 低 | 对话历史全量加载到内存，长时间运行可能 OOM |

### 2.3 防外部侵入的完整方案

```
┌────────────────────────────────────────────────────┐
│                  Harven AI 安全洋葱模型              │
├────────────────────────────────────────────────────┤
│  第1层：消息入口                                      │
│  ├─ 功德行 LLM 意图分析（所有消息必经）                  │
│  ├─ requireApproval 危险操作确认                     │
│  └─ SSRF 防护：拦截内网地址请求                        │
├────────────────────────────────────────────────────┤
│  第2层：外部数据输入                                   │
│  ├─ 文件类型白名单（禁止 .exe/.dll/.ps1 等）           │
│  ├─ 脚本/宏扫描（.docm/.xlsm 中的 VBA）               │
│  ├─ 内容安全扫描（恶意 URL、混淆代码）                  │
│  └─ 文件大小限制 + 格式校验                            │
├────────────────────────────────────────────────────┤
│  第3层：代码执行隔离                                   │
│  ├─ Docker 容器优先（256MB内存、只读、网络隔离）        │
│  ├─ 子进程降级（黑名单扫描、15秒超时）                  │
│  └─ 执行日志审计                                     │
├────────────────────────────────────────────────────┤
│  第4层：外部通信                                      │
│  ├─ 速率限制（API 调用频率控制）                       │
│  ├─ 熔断器（连续失败自动暂停）                         │
│  ├─ 超时控制（所有外部调用 max 30s）                   │
│  └─ 出站过滤（禁止访问内网 IP）                        │
├────────────────────────────────────────────────────┤
│  第5层：系统稳定性                                    │
│  ├─ Ollama 进程守护（自动重启）                       │
│  ├─ 内存监控（对话历史 LRU 淘汰）                      │
│  ├─ 健康检查（定期心跳检测）                           │
│  └─ 优雅降级（模块失败不影响主服务）                    │
└────────────────────────────────────────────────────┘
```

### 2.4 AI 自身不崩溃的保障

当前 Harven AI 已经很稳定，但仍有几个风险点：

| 风险 | 现状 | 改进 |
|------|------|------|
| **Ollama 进程崩溃** | 无守护，需手动重启 | 加 watchdog 进程监控，自动重启 |
| **云端 API 宕机** | `active_provider` 自动回退 Ollama | ✅ 已有，但需确保云端路径也走这个兜底 |
| **SQLite 锁死** | WAL 模式已启用 | ✅ 已处理 |
| **内存 OOM** | 对话历史无限加载（`_load_history` limit=100） | 改为 LRU + 最大内存限制 |
| **无限循环** | 代码沙箱15秒超时 | ✅ 已处理 |
| **敏感操作误删** | requireApproval | ✅ 已处理 |
| **磁盘满** | 无监控 | 加磁盘空间告警 |

## 四、回答你的两个问题 —— 一句话版

### Q1：AI 链接大模型，到底谁在回答？

**Harven AI（助理层）+ 大模型（大脑层）= 共同回答。** Harven 负责"知道你不知道的事"（记忆、知识库、安全、身份），大模型负责"组织语言"。最合理的做法是让每条消息都走助理层的预处理和后处理，不管背后用本地还是云端模型——**这个当前没做对，需要修**。

### Q2：下载外部内容如何保证安全？AI 如何不崩溃？

**六层防护洋葱模型**：入口安全→输入过滤→执行隔离→通信控制→系统守护→数据隔离。龙虾（OpenClaw）只有 Docker 一层，Harven AI 已有功德行+三库+设备绑定三层，再加 SSRF/速率限制/守护进程三层就完整了。核心改动就两个：①统一消息路径让云端也过安检 ②加内网 IP 过滤。
