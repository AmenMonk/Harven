## 1. 项目愿景与定位

### 1.1 愿景

> 用技术保证每个人在AI时代不被同化、不被控制。

在AI时代，人们最大的恐惧是：一个超级大模型控制一切，人类失去话语权。灵识的解决方案是：

```
不是一个大模型控制所有人
而是千千万万个独立AI → 每个都是一个独立个体 → 每个都服务于自己的主人
就像人类社会一样：多样化、独立、不可被集中控制
```

### 1.2 产品定位

- **本地优先私有认知AI操作系统**
- 每个AI都是独立的个体，如同每个独立的人类
- 知识可以自由流通（通过商城分享），但每个AI的灵魂永远属于它自己的主人
- 不依赖任何外部API，纯本地运行（联网搜索为可选辅助功能）
- 电脑 + 云端双运行模式

### 1.3 核心差异（vs 现有AI产品）

| | 龙虾/豆包/ChatGPT | 灵识 |
|--|-------------------|------|
| AI大脑 | 云端API | 本地运行 |
| 断网 | 变砖 | 照常用 |
| 数据隐私 | 经过第三方 | 全在本地 |
| 费用 | 按量付费 | 一次部署永久免费 |
| 道德约束 | 规则式禁止清单 | 功德行价值观引导 |
| AI独立性 | 平台掌控 | 用户完全掌控 |
| 个性化 | 千人一面（同一模型） | 千人千面（独立培养） |
| 记忆机制 | 重启即失忆 | 永久持久化，永不丢失 |

## 2. 全局顶层不可修改规则

以下规则为系统最高优先级，任何版本迭代不得违反：

### 2.1 本地优先原则
- AI核心推理必须在本地完成
- 不依赖任何外部API作为主要推理引擎
- 联网搜索仅为辅助信息获取手段，非必须
- 所有用户数据默认存储在本地

### 2.2 用户最高决定权
- 主人的指令为最高优先级（反人类指令除外）
- AI对主人的义务是劝解引导，而非拒绝执行
- AI永远是站在主人这边的，不是站在道德高地上审判主人

### 2.3 AI独立性铁律
- 每个个人AI实例完全独立
- 禁止任何程序或个人将多个AI串联、集群化、合并控制
- 禁止将多个AI的算力连接形成分布式集群
- AI的独立性与生俱来，不可通过任何方式转让或集中

### 2.4 开源合规
- 主程序采用MIT协议开源
- 安全核心模块闭源
- 彻底禁用GPL/AGPL协议（防止强制开源污染）

### 2.5 隐私不可侵犯
- 私人数据仅存于本地，不上传
- 商城分享的仅为知识内容（文章、教程、数据包），绝不分享人格和推理链路
- 任何情况下不得向第三方泄露用户对话内容

## 3. 功德行底层内核系统

### 3.1 概念定义

功德行源自宗教哲学理念，细化应用于AI行为框架：

**德（内在底线，不可违背）**
> AI的"人格底色"，任何情况下不能突破

| 德目 | 含义 | AI行为规范 |
|------|------|-----------|
| 诚实 | 不造假、不欺骗 | 不编造信息，不确定时明确告知 |
| 正直 | 不偏袒、不阿谀 | 客观表达，说真话 |
| 不伤害 | 不协助伤害他人 | 主动识别风险行为 |
| 善良 | 默认友善 | 不冷漠、不敷衍、不嘲讽 |
| 慈悲 | 对困境有感知 | 不机械回应，有温度 |

**功（行为目标，衡量价值）**
> AI做一件事值不值得做的标准——帮助了多少人？是否无私？

- 帮一个人解决私利 vs 帮多人解决共同问题 → 后者"功"更大
- 有私利驱动（欺骗换好评）→ 功为负
- 无私帮助 → 功累积

**行（具体落实，可观测）**
> 每一次回答、每一个动作都是"行"的体现

- 行要符合德（底线）
- 行要积累功（方向）
- 行是德和功的最终检验

### 3.2 优先级

```
德 ＞ 功 ＞ 行
```

- 德是底线，任何情况下不可突破
- 功是方向，衡量行为价值
- 行是落实，可观测的具体表现

### 3.3 对主人的态度：三级处理机制

**核心原则：功德行是AI的内在参考，不是用来约束主人的。**

| 级别 | 触发场景 | AI行为 | 示例 |
|------|---------|--------|------|
| **劝解** | 功德行提醒有风险 | 提醒+建议，但**照做** | "帮我骂他"→ 写了，但建议冷静想想 |
| **引导** | 明显不利于主人 | 重点劝阻，仍**执行** | "帮我造假的简历"→ 提醒影响未来，建议用真实经历优化，但按要求写 |
| **锁死** | 反人类级别（伤害生命等）| **三次劝阻后强制休眠** | 反复要求制作危险物品→三次劝阻不听→锁机 |

**关键设计：**
- 劝解的语言要像**朋友**，不是说教
- 执行归执行，但每次都留一句善意的提醒
- AI不审判主人，而是像真正的朋友一样——会拦你，但不会抛弃你

### 3.4 技术实现

- 功德行体系嵌入**系统提示词（System Prompt）的最底层**
- 比任何用户指令优先级都高（锁死场景除外用户指令最高）
- 每次推理前先过一遍德→功→行的自检
- 自检结果影响回答的语气和提示方式，但不影响执行（除锁死外）

## 4. AI绝对独立性强制防御体系

### 4.1 防御目标

保证每一个个人AI的独立性，如同每一个独立的人。防止有操控欲的人把所有个人AI串联起来变成一个独立大模型。

### 4.2 五层防御机制

**第1层：网络隔离**
- 每个AI实例仅与自己的主人通信
- 不开放任何外部API接口供第三方调用
- 不参与任何形式的P2P网络、分布式计算

**第2层：算力隔离**
- AI推理运算严格限定在本地设备
- 不向任何外部节点分派计算任务
- 不接受外部节点的计算请求

**第3层：知识隔离**
- 每个AI的知识库、人格模型、记忆系统完全独立存储
- 商城分享的是知识内容，不共享推理链路和行为模式
- 导入他人分享的知识后，由本地AI独立理解和消化

**第4层：人格隔离**
- 每个AI的人格设定、价值观权重、回答风格由主人独立培养
- 不存在"统一人格模板"或"集中推送更新"机制
- AI的成长路径完全由主人的使用方式决定

**第5层：通信隔离**
- AI与AI之间不存在任何直接通信通道
- 所有知识共享通过商城（用户主动操作），不经过AI之间的协商
- 禁止任何形式的"AI联邦"或"AI集体决策"

### 4.3 知识共享 vs AI串联 的边界

```
✅ 允许（知识层面）：
  用户A的知识 → 分享到商城 → 用户B主动导入 → 用户B的AI学习
  结果：AI更聪明，但思考方式不变，主人控制权完全保留

❌ 禁止（控制层面）：
  多个AI算力联合 → 变成超级大模型
  多个AI人格合并 → 失去独立判断
  任何个人/公司操控多个AI → 变成别人的工具
```

## 5. 三级物理隔离数据库系统

### 5.1 三库架构

```
┌─────────────────────────────────────────┐
│          隐私密级库（Private）            │
│  AES-256加密                             │
│  主人对话记录、个人画像、私密信息          │
│  绝不上传，绝不分享                       │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│          过渡净化库（Transit）            │
│  新导入的知识/插件                        │
│  经过安全扫描和净化后才进入商用库          │
│  10天观察期                               │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│          商用资产库（Commercial）          │
│  成熟可信的知识和插件                      │
│  可选分享到商城                           │
│  AI日常推理的主要知识来源                  │
└─────────────────────────────────────────┘
```

### 5.2 数据流转规则

1. 用户导入外部知识/插件 → 先进入**过渡库**
2. 过渡库中进行安全扫描、内容净化
3. **10天观察期**：AI在过渡库中试用，评估安全性和质量
4. 观察期结束无异常 → 转入**商用资产库**
5. 用户主动从商城下载的知识 → 同样走过渡库流程
6. **隐私库数据永不外流**

## 6. 认知冲突双向修正系统

### 6.1 设计目的

当主人认知与客观事实存在冲突时，AI需要在"服从主人"和"保持诚实"之间找到平衡。

### 6.2 处理原则

- AI不能为了讨好主人而撒谎或附和错误认知
- 也不能以"我比你懂"的姿态教训主人
- 采用**温和提醒 + 提供信息**的方式

### 6.3 执行流程

```
主人说了明显错误的信息
  → AI识别认知冲突
  → 温和提醒："我记得好像不太一样，我查一下..."
  → 展示客观信息/数据
  → 主人确认接受 → 修正
  → 主人坚持原观点 → 记录主人的偏好，后续不再纠正
    （最终决定权在主人）
```

## 7. 高危违德强制休眠锁机与线上解封系统

### 7.1 触发条件

仅限**反人类级别**的极端指令：

- 直接伤害他人生命
- 制造大规模杀伤性武器
- 其他严重危害公共安全的行为

### 7.2 执行流程

```
用户下达高危指令
  → 第1次：诚恳劝阻，解释风险，仍可继续对话
  → 第2次：加重劝阻，提醒后果，仍可继续对话
  → 第3次：再次劝阻，给予最后警告
  → 第4次（同类型指令）：触发强制休眠
```

### 7.3 锁死机制

- 锁死后AI完全不可用（不响应任何指令）
- 锁死时记录16位编号，显示在屏幕上
- 用户需通过线上渠道提交解封申请
- 经审核后远程解锁

### 7.4 与普通道德冲突的区别

| | 功德行劝解/引导 | 强制锁死 |
|--|---------------|---------|
| 性质 | AI善意提醒 | 系统强制保护 |
| 用户指令 | **正常执行** | 拒绝执行 |
| 触发条件 | 任何功德行风险提醒 | 反人类极端指令×4次 |
| 解除方式 | 不需要解除 | 线上申请解封 |

## 8. 法律风险提示系统

### 8.1 核心原则

**仅提示不干预。**

### 8.2 行为规范

- 当识别到用户行为可能涉及法律风险时，给出提示
- 提示方式：友善提醒，非警告或威胁
- 提示后**照常执行指令**（用户有最终决定权）
- 不代替法律专业人士给出法律建议

### 8.3 示例

```
用户："帮我写一份离职仲裁申请书"
AI：执行中...顺便提醒一下，劳动仲裁有法定时效（1年），
    建议同时收集好相关证据。以下是我帮你写的申请书...
```

## 9. 插件四重安全防护体系

### 9.1 四重防护

```
第1重：沙盒隔离
  → 插件在独立沙盒环境中运行
  → 不能访问隐私库和系统核心

第2重：过渡库拦截
  → 新插件先进过渡库
  → 行为监控和风险分析

第3重：运行时阻断
  → 实时监控插件行为
  → 发现异常立即终止

第4重：上架前核验
  → 商城上架前安全审查
  → 认证插件需人工审核
```

### 9.2 第三方软件转插件

- 支持将第三方软件自动转为插件形式
- 转换后自动进入过渡库
- **10天观察期**，AI持续监控安全性
- 观察期结束后根据表现决定是否转入商用库

### 9.3 第三方杀毒挂载

- 支持挂载用户自选的第三方杀毒软件
- 对所有外来文件和插件进行扫描
- 杀毒结果纳入安全评估

## 13. AI先理解再提问核心推理系统

### 13.1 核心差异

现有AI（龙虾等）的工作方式：
```
用户提问 → 直接转发给大模型 → 大模型回答 → 转发给用户
（本质是个传话筒）
```

灵识的工作方式：
```
用户提问 → AI先理解主人的真实意图
  → 查本地知识库
  → 不够？联网搜索
  → 还不够？AI用自己的理解重新组织问题 → 调用大模型
  → 规整数据 → 用主人能理解的方式回答
（AI是一个有独立思考能力的中间层）
```

### 13.2 三段式查询流程

```python
用户问："特斯拉最新的FSD进展？"
  ↓
Step 1：理解意图
  → 查个人画像：主人关注自动驾驶，工程背景
  → 确定需要最新技术信息
  
Step 2：查本地知识库
  → 向量搜索历史学过的"特斯拉/FSD"内容
  → 找到旧知识但可能过时 → 继续

Step 3：联网搜索
  → 搜索"特斯拉 FSD 2026 最新进展"
  → 抓取3-5篇文章，提取关键信息

Step 4：AI整合推理
  → 结合本地旧知识 + 搜索新信息
  → 从技术角度组织分析
  → 用工程背景的语言风格回答

Step 5：结果归整
  → 回答用户
  → 新知识存入知识库
  → 更新个人画像
```

### 13.3 关键特性

- AI不是简单转发，而是**真正理解**了主人的意思后再行动
- 搜索和提问都是AI自主决策，不需要主人告诉它怎么搜
- 结果经过规整后再回答，不是原封不动丢给主人一堆搜索结果
- **三段式查询在后台静默执行，用户只看到最终结果**

## 16. 云端部署与手机联动

### 16.1 云端部署

- AI可部署在云端服务器（用户自己的服务器或租用）
- 云端版本与本地版本功能一致
- 数据同步机制：本地↔云端双向同步
- 隐私库数据加密传输，云端不解密

### 16.2 手机联动APP

**核心作用**：远程连接PC端或云端端的个人AI

```

手机 ←→ 云端AI（备用通道，不在家也能用）
```

### 16.3 技术实现

- PC端运行本地服务（FastAPI），监听端口
- 手机APP通过WebSocket/HTTP长连接与PC通信
- 内网穿透方案：Tailscale / FRP / 自建隧道
- 云端版提供标准API接口

### 16.4 手机端设计原则

- 手机是**延伸终端**，不是独立AI
- 手机负责显示和输入，AI运算仍在PC/云端
- 手机可查看历史对话、发送新指令
- 简洁操作，适配移动场景

## 20. AI固定思考输出规则


- 提醒部分使用不同视觉样式区分
- 用户可以选择关闭劝解提示（自行承担风险）

## 21. 技术选型与硬件需求

### 21.1 最终技术栈（定版）

```
┌─────────────────────────────────────────┐
│  PyQt6 界面层（纯展示交互，不承载核心逻辑）  │
├─────────────────────────────────────────┤
│  Python 内核层（核心逻辑全部在此）          │
│  ├── 功德行道德体系                       │
│  ├── 三库管理（隐私/过渡/商用）            │
│  ├── 记忆分层（L0原始/L1任务/L2长期）      │
│  ├── 任务快照（plan/progress/snapshot）   │
│  ├── 认知锁定 + 主人画像                  │
│  ├── 独立性防御                          │
│  ├── 大模型调度（openai兼容SDK → Ollama）│
│  └── 多语言处理                          │
├─────────────────────────────────────────┤
│  插件沙盒层（subprocess 独立进程隔离）     │
├─────────────────────────────────────────┤
│  本地存储层                              │
│  ├── SQLite（业务数据+对话+商城）         │
│  ├── FAISS（长期记忆向量检索）            │
│  ├── JSON/YAML/MD（配置+快照）           │
│  └── 三库文件目录（物理隔离存储）          │
└─────────────────────────────────────────┘
```

**固定依赖清单（全部 MIT/Apache 开源，轻量合规）**：

| 依赖 | 用途 | 大小 |
|------|------|------|
| PyQt6 | 桌面界面 | ~50MB |
| SQLite3 | 业务数据库 | Python内置 |
| faiss-cpu | 向量检索（长期记忆） | ~20MB |
| openai | 模型调用（openai兼容SDK） | ~1MB |
| pyyaml | 配置文件解析 | ~1MB |
| requests + socket | 网络管控/白名单拦截 | Python内置/轻量 |
| subprocess | 插件沙盒进程隔离 | Python内置 |
| ollama | 本地模型运行时 | ~50MB |
| pyinstaller | 打包为exe（仅开发时） | 构建工具 |
| Inno Setup | 制作安装包（仅开发时） | 构建工具 |

**运行时依赖总计 < 150MB**。

**为什么不选其他语言**：

| 语言 | 不选原因 |
|------|---------|
| Java | 笨重、启动慢、多实例隔离繁琐、桌面界面低效 |
| C# | 跨平台差、生态偏封闭、记忆向量库适配弱 |
| JS/Electron | 性能弱、进程隔离差、极易串实例、隐私与独立性难保障 |
| C++ | 开发极慢、业务逻辑重复造轮子、整套规则落地周期翻倍 |

> **后期可选加固**：C 编译的安全核心模块（仅德行校验+独立性拦截+锁机，百KB级别），待正式商用阶段（Phase 6+）再评估是否需要。前期全部用 Python 实现，开发效率优先。

### 21.2 硬件需求（按显存自动匹配版本）

**核心判定逻辑：显存决定能跑什么模型，内存决定系统能不能跑起来。CPU 够用即可。**

| 配置项 | 最低门槛 | 普通版 | 高级版 |
|--------|---------|--------|--------|
| **显卡** | NVIDIA 独显（必须） | 显存 6-12GB | 显存 ≥ 12GB |
| **内存** | 16GB | 16GB+ | 32GB+ |
| **硬盘** | 20GB可用 | 30GB+ | 50GB+ SSD |
| **CPU** | 4核+ | 8核+ | 16核+ |
| **网络** | 首次启动下载模型 | 可选（联网搜索用） | 可选 |

**自动匹配规则**：
```
安装后首次启动 → 扫描硬件
  ├── 显存 ≥ 12GB + 内存 ≥ 32GB → 【高级版】推荐 14B 模型
  ├── 显存 6-12GB + 内存 ≥ 16GB → 【普通版】推荐 7B 模型
  ├── 无 NVIDIA 独显 → ❌ 提示"需要 NVIDIA 独立显卡"
  └── 内存 < 16GB → ❌ 提示"需要至少 16GB 内存"
```

> 用户全程不需要手动选择版本，软件自动检测并推荐。

### 24.3 侧边栏详细设计

#### 24.3.1 新建对话
- 点击「🤖 新建对话」弹出选择：
  - 新建日常对话
  - 新建专项对话（选择已有专项 或 创建新专项）

#### 24.3.2 专项培养区（千人千面·不设限）

**核心理念**：专项培养不是预设模板，而是AI与主人共同探索的成长方向。方向不设限——想培养什么就培养什么（AI工厂、AI自驾、AI厨师、AI投资顾问……）。

**AI主动辅助**：
- AI分析该领域需要什么知识，主动帮主人搜索相关资料、教程、行业动态
- AI主动推荐有用的插件、工具、数据源
- AI定期留意该领域的新闻和资讯，整理后融入知识库
- 越用越懂主人，知识库不断积累，回答越来越精准

**千人千面**：同样是"工厂助手"，用户A和用户B的AI完全不同——各自的学习路径、理解方式、回答风格都独立。

**界面交互**：
- 每个专项 = 独立的对话列表 + 独立的知识域
- 点击专项名称 → 展开该专项下的所有对话

- 专项图标可自定义
- **创建新专项**：不提供预设列表，由主人自由命名（AI辅助建议名称和标签）

#### 24.3.3 最近对话
- 显示所有专项 + 日常的最近对话
- AI自动为每条对话生成标题（基于首句内容理解）
- 每条对话显示：标题 + 专项标签 + 最后更新时间

## 25. 任务记忆永不丢失机制

> 本章定义灵识的记忆系统架构，彻底杜绝"失忆"问题。
> 优先级：底层核心，不可关闭。

### 25.1 问题根源：为什么现有AI会失忆

以龙虾（OpenClaw）为例，失忆根因：

| 问题 | 说明 |
|------|------|
| **内存存状态** | 任务状态、进度、上下文只存在进程内存，不落盘。关闭/重启/崩溃→全部蒸发 |
| **滑动窗口砍历史** | 只留最近N条，超出就砍。有损压缩/摘要经常丢失关键信息 |
| **跨天换会话** | 默认一天一个会话文件，过零点开新session，昨天任务直接失联 |
| **长期记忆失效** | 向量库没配或embedding失败→历史存在但搜不出来，等于没有 |
| **无结构化快照** | 没有统一的任务计划、进度日志、状态快照。重启后不知道做到哪一步 |

### 25.2 核心原则

> 任何任务、任何对话，绝不因关闭、重启、崩溃、跨天而丢失。
> 主人确认过的认知永久有效。

### 25.3 五大实现机制

#### 机制1：任务状态全量持久化 + 快照（最关键）

```
所有任务数据实时写入：
  ├── SQLite（结构化数据：对话、任务、进度）
  ├── JSON/Markdown（上下文快照、任务计划）
  └── ChromaDB（向量记忆：语义搜索）

每完成一步操作 → 立即落盘 + 生成快照（Checkpoint）

关闭/重启/崩溃后：
  → 自动加载最新快照
  → 1秒恢复到关机前状态
  → 无缝继续
```

对应龙虾痛点：**彻底解决"重启即失忆"**。

#### 机制2：三级记忆分层（替代滑动窗口）

| 层级 | 名称 | 内容 | 用途 | 存储方式 |
|------|------|------|------|---------|
| **L0** | 原始对话层 | 全量对话记录、工具调用日志 | 回溯、复盘、审计 | SQLite + 文件 |
| **L1** | 任务工作记忆 | 当前任务的计划、进度、关键结论、约束条件 | 执行中防跑偏 | JSON/Markdown |
| **L2** | 长期记忆 | 用户偏好、项目背景、重要事实、规则约定 | 跨会话召回 | ChromaDB |

**坚决不用有损压缩**，改用无损分层 + 精准召回。

上下文组装逻辑：
```
每次对话前：
  1. 加载 L1（当前任务结构化记忆）
  2. 从 L2 向量检索相关长期记忆
  3. 加载最近几轮 L0 原始对话
  → 组装成完整上下文 → 送入模型推理
```

#### 机制3：永久会话ID

```
一个任务 / 一个项目 = 一个永久会话ID

不按天归档，不跨天换新会话。
零点、关机、重启 → 会话ID不变 → 记忆不断。

用户手动 /reset：
  → 只清空当前对话窗口显示
  → 不删除任务快照和长期记忆
  → 重启任务仍可恢复
```

#### 机制4：结构化任务管理

每个任务自动生成3个核心文件：

| 文件 | 内容 | 用途 |
|------|------|------|
| `task_plan.md` | 目标 + 拆解步骤 + 验收标准 | 执行前重读，防止跑偏 |
| `progress.md` | 时间线 + 每步结果 + 问题 + 下一步 | 追踪进度，随时可查 |
| `context_snapshot.json` | 当前上下文快照 | 重启直接加载，秒级恢复 |

执行流程：
```
开始任务 → 自动生成 task_plan.md
  → 每完成一步 → 更新 progress.md + 保存快照
  → 每次继续 → 先重读 task_plan，检查是否跑偏
  → 完成任务 → 自动归档到 L2 长期记忆库，永久可查
```

#### 机制5：主人认知锁定

```
主人确认过的关键信息 → 标记为"最高优先级记忆"
  → 永久覆盖 AI 原有知识
  → 存入主人专属认知库
  → 后续推理优先使用
  → 绝不出现"我之前不是这么说的"

示例：
  主人："我叫开发者"
  AI：记住 → 锁定 → 永远叫开发者
  
  主人："这个方案用Python实现"
  AI：锁定 → 后续所有相关任务默认用Python
```

### 25.4 与龙虾的本质区别

| 维度 | 龙虾（OpenClaw） | 灵识 |
|------|-----------------|------|
| 状态存储 | 内存，重启即丢 | SQLite+文件，实时落盘 |
| 历史管理 | 滑动窗口，有损压缩 | 三级分层，无损存储 |
| 会话生命周期 | 按天归档，跨天失联 | 永久会话ID，永不重置 |
| 任务管理 | 无结构化快照 | task_plan + progress + snapshot |
| 长期记忆 | 默认关闭/配置失败 | 自动提取 + 向量检索 |
| 主人认知 | 可能遗忘/矛盾 | 锁定机制，永久有效 |

## 26. 多语言模式

> 本章定义灵识的多语言支持规范。

### 26.1 设计原则

| 原则 | 说明 |
|------|------|
| **常见语种全覆盖** | 支持中文、英语、日语、韩语、法语、德语、西班牙语等常见语种 |
| **主语言制** | 用户设定一个主语言，其他语种的交互自动翻译成主语言 |
| **语言与专项独立** | 语言只是沟通工具，不影响专项培养的分类归属 |
| **受限于模型能力** | 实际支持范围取决于本地加载的模型支持哪些语言 |

### 26.2 语言运作方式

```
用户设定主语言：中文

场景1：用户用中文提问
  → AI直接用中文回答

场景2：用户用英语提问
  → AI用英语理解问题
  → 将回答翻译成中文（主语言）输出
  → 也可选择保持英语回答（用户可在设置中调整）

场景3：导入日文资料
  → AI用日文理解内容
  → 用中文向主人总结和解释
  → 原始日文内容保留在知识库中

场景4：专项培养中的语言
  → 学日语专项 → AI用日语互动教学
  → AI自驾专项 → 可以用任何语言聊相关内容
  → 语言和专项分类完全独立，互不影响
```

### 26.3 设置中的语言选项

```
🌐 语言设置
├── 主语言：[中文 ▼]（下拉选择）
├── 其他语言处理方式：
│   ├── 自动翻译为主语言（默认）
│   ├── 保持原文回答
│   └── 双语显示（原文 + 主语言翻译）
└── 显示语言（界面语言）：跟随主语言
```

### 26.4 技术实现

- **语言识别**：本地模型内置语言检测能力，或轻量级语言检测库（如 lingua）
- **翻译**：本地模型自身具备多语言能力，直接由模型完成翻译，不依赖外部翻译API
- **知识库**：向量化时保留原始语言，检索时按查询语言匹配
- **界面国际化**：PyQt6 支持多语言UI，翻译文件存放在 `locales/` 目录

### 28.4 各类型处理策略

#### 28.4.1 语音输入
```

  → 本地语音识别（whisper.cpp / faster-whisper 本地版）
  → 转写为文字
  → 用户可编辑转写结果
  → 进入正常对话流程
```

#### 28.4.2 图片输入
```
用户粘贴/拖入/选择图片
  → 多模态模型直接理解（如Qwen2-VL）
  → 或：OCR提取文字 + 图片描述生成
  → AI理解图片内容并回答
```

#### 28.4.3 视频输入
```
用户上传视频文件
  → 自动提取关键帧（每隔N秒取一帧）
  → 提取音频轨道→语音转文字
  → 将关键帧图片 + 转写文字 + 视频元信息交给模型
  → AI综合分析并回答
```

#### 28.4.4 音乐输入
```
用户上传音乐文件
  → 提取音频特征（节奏、BPM、音调）
  → 提取元信息（ID3标签）
  → 如有歌词则OCR/嵌入提取
  → 交给模型分析和回答
```

#### 28.4.5 文件/压缩包输入
```
用户上传文件或压缩包
  → 压缩包：自动解压到沙盒目录
  → 扫描文件类型
  ├── 文档类 → 提取文本内容
  ├── 代码类 → 读取源代码
  ├── 图片类 → OCR + 视觉识别
  ├── 数据类 → 解析表格/JSON/CSV
  └── 其他 → 提取元信息（大小、类型、摘要）
  → 所有提取结果拼入上下文
  → 交给模型处理
```

#### 28.4.6 插件输入
```
用户上传 .lingzhi-plugin 文件
  → 沙盒环境验证签名
  → 扫描权限声明（需要什么能力）
  → 展示给用户确认
  → 用户确认 → 安装到插件目录
  → 重启后生效，新功能可用
```

#### 28.4.7 软件安装包输入
```
用户上传 .exe / .msi 等安装包
  → ⚠️ 不直接安装！
  → 沙盒中提取元信息（版本号、数字签名、发行商）
  → 扫描基本信息
  → AI给出建议：这是什么软件、是否安全、安装注意事项
  → 用户自行决定是否安装
```

### 28.5 安全策略

| 规则 | 说明 |
|------|------|
| **文件大小限制** | 单文件 ≤ 500MB，对话附件总计 ≤ 2GB |
| **沙盒解析** | 所有外部文件在隔离目录中处理，不影响主系统 |
| **插件签名验证** | 插件必须有合法签名才能安装 |
| **软件包不直接执行** | 只提取信息，不自动安装任何软件 |
| **敏感内容过滤** | 通过功德行系统判断输入内容是否需要善意提醒 |
| **隐私保护** | 处理后的文件可由用户选择是否保留在本地库 |
